# 通知雷达 NoticeRadar — 作品说明

> 北京邮电大学第一届人机协作编程大赛暨华为开发者大赛-北京邮电大学站
> 参赛队：通知雷达（单人队）　作者：刘博　信息与通信工程学院 通信工程 26 级

## 一句话

**粘一条校园通知，30 秒内告诉你：什么时候截止、值不值得花时间、下一步做什么、依据是哪条规定。**

## 一、问题从哪来

2026 年 9 月，我因为漏看学院群里的一条通知，错过了一届全国大学生数学竞赛；此前也错过外研社杯短视频大赛。

复盘下来，问题不是"没有信息"，而是：**信息散在群聊、门户、公众号里，窗口只有两三天，而且没人告诉你这条值不值得花时间。**

市面上的校园信息工具停在"帮你查"——问答机器人、课表助手、通知聚合。它们解决的是"找得到"，没解决"要不要"。

通知雷达做的是**"帮你决定"**：输出判断，而不是输出字段。

**我是这个产品的第一个用户，也是最大的受害者。这是它最硬的立足点。**

## 二、它到底做什么

输入：一条从群里复制粘贴的通知原文（格式乱、带转发前缀都行）。

输出一张决策卡：

| 输出 | 说明 |
|---|---|
| 倒计时 | 距截止几天；有多个截止节点时全部列出（报名截止 / 提交截止分开算） |
| 匹配度 | 0–100，按"北邮通信工程大一、目标保研"的画像打分，每个加减分都有理由 |
| 结论 | 六档：强烈建议 / 可以考虑 / 不建议 / 已截止 / 信息不足 / 待核实。前四档由分数与截止状态决定，后两档是"不敢下结论"时的诚实出口 |
| **判断依据** | 引用知识库中的校内规定原文（文件名 + 章节），**召回不到就明说"知识库未收录"，不编** |
| 风险 | 组队要求、指导教师、时间冲突、加分不确定性 |
| 行动清单 | 具体到"今天做什么"，不是"建议关注" |
| **自审结果** | 字段矛盾会被拦下、打回重跑，并把矛盾原因显示出来 |
| 日历 | 一键导出 .ics，自带提前 3 天 + 1 天双提醒 |

## 三、五个 Agent，不是一次 API 调用

```
        用户粘贴通知
             │
    ┌────────▼────────┐
    │ ① Extractor     │  LLM 优先 + 规则兜底，双通道抽取 7 个字段
    └────────┬────────┘
    ┌────────▼────────┐
    │ ② Validator     │  日期合法性 / 是否过期 / 字段完整度 → confidence
    └────────┬────────┘
    ┌────────▼────────┐
    │ ③ Retriever     │  知识库 BM25 检索，召回真实条款片段（带来源）
    └────────┬────────┘
    ┌────────▼────────┐
    │ ④ Evaluator     │  结合画像 + 召回条款打分，输出判断与行动
    └────────┬────────┘
    ┌────────▼────────┐
    │ ⑤ Critic        │  审查 ①④ 的结果，发现矛盾 → 打回重跑
    └────────┬────────┘
             ▼
      决策卡 + .ics
```

**为什么要有第 ⑤ 个 Agent**：单独一次大模型调用，错了没人管。Critic 是专职对账的角色，能抓住三类硬矛盾——

1. 截止日期已过，却判断"可以报名"
2. 活动时间早于截止日期（活动都结束了还能报名，字段必然有一处错）
3. 标题都没抽到，却给出"强烈建议"（结论建立在信息缺口上）

抓到就打回重跑，两轮还修不好就明确标注"仅供草稿参考"，**不装作已经审过**。这是现场可演示的。

**为什么检索不用向量库**：知识库只有几十条切片，中文二元组 BM25 的精度与向量检索相当，但零依赖、零部署、可解释（能打印命中了哪些词）。五天工期下，这是唯一正确的工程选择。

## 四、用码道是怎么做出来的（核心留痕）

> 完整 12 轮对话见码道工程「Flask 搭建 notice-radar 项目骨架」，截图按轮次编号。
> 开发方式：**一条 prompt 只做一件事**，跑通再进下一条；每条都要求贴原始输出，不接受"已完成"三个字。

| 轮次 | 目标 | 实际发生了什么 |
|---|---|---|
| 1 | Flask 骨架 + 假数据 | 通过，但它自作主张做成**批量列表 + summary 统计接口** |
| 2 | 改契约为单条决策 | 通过。但我逐行读代码发现仍有 4 处不符：`critic.verdict` 写成中文句子、`round` 写成 `rounds`、缺 `fallback`、枚举非法值直接 `raise`（会 500 白屏） |
| 3 | 删假数据，接真规则解析 | **撞出真 bug**：「每个团队参赛人数 1-3 人」被短日期正则当成 1 月 3 日，`days_left = -316`，真正的 11-14 / 11-20 全漏抽 → 修后 2 个节点、`days_left = 5` |
| 4 | 3 个缺陷 + 大模型通道 | **撞出真 500**：prompt 里的 `{"label": ...}` 被 `str.format` 当占位符，`KeyError` 落在 `try` 外 → 改成 `.replace()` 并纳入兜底。假 key 实测真打到 `api.deepseek.com` 拿到 401，0.116s 后回退 |
| 5 | 校验层 validator | 通过。必填项按类别区分，讲座不再被误判"缺字段"；`confidence` 废掉，改三档 `level` |
| 6 | 评估层 evaluator | 通过。资格判定前移到打分之前；四条用例：竞赛 65 分强烈建议 / 讲座 50 可以考虑 / 青年教师赛 10 分不建议 / 停水 10 分不建议 |
| 7 | 日历导出搬到服务端 | 通过。2 VEVENT、4 VALARM、最长行 75 字节、零裸 LF、零 `\u` 转义 |
| 8 | 检索器 + 知识库 | 通过。竞赛命中 3 条（4.94 / 4.16 / 3.18），讲座 0 命中且**明确返回空，没有降阈值凑引用** |
| 9 | 自审 Agent Critic | **现场演示的核心**：矛盾通知 R1 `reject`（E2 时间冲突）→ 打补丁 → R2 `pass`，结论自动降为「待核实 / 30 分」 |
| 10 | 前端 + 两个真 bug | 自审拦截历史要留痕（不能再只显示"通过"）；赛程节点独立成 `milestones` 灰色时间轴；跨行取日期收紧到文末落款区 |
| 11 | **两条没见过的真实通知压测** | 又抓出两个 bug：停水的 `event_date` 被"发布时间"那行污染；「11 月 28、29 日至 12 月 5、6 日」顿号多日期只抽到 28 和 5，丢了 29 和 6 |
| 12 | 交付自查 | 8 项逐条给证据：400 不 500、降级仍 200、无命中 `grounded=false`、重试上限 1 轮、空日历返 400、无 `.pyc`、零假数据残留、端到端 2.4–2.9 ms |

### 人对 AI 的 5 次否决（这一栏才是"人机协作"）

| # | AI 的产出 | 我为什么否掉 | 改成什么 |
|---|---|---|---|
| 1 | 批量通知列表 + 统计接口 | 定位是"帮你决定这一条"，不是"给你一个通知聚合器"；多截止节点、引用依据、自审矛盾塞不进列表卡片 | 单条深度决策契约 |
| 2 | `critic.verdict` 写成中文句子 | 主流程要靠 `verdict === 'reject'` 判断是否打回重跑，中文句子没法用代码判断 | `pass / reject` + 单独的 `summary` 字段 |
| 3 | 枚举非法值 `raise ValueError` | 用户粘一条没见过的通知就 500 白屏，与"降级不能让页面报错"自相矛盾 | 兜底到「信息不足」+ `E_ENUM_FALLBACK` 警告 |
| 4 | 自审拦截后仍显示"强烈建议 90 分" | 同一屏上自相矛盾，一眼被看穿 | E2 打补丁时同步降级 worth 与 score |
| 5 | 分数 65 却叫"强烈建议"、30 分叫"可以考虑" | 阈值和结论脱节，和上一条同一种毛病 | worth 由 score 阈值决定，资格不符/已过期/信息不足才走覆盖档 |

> **评委最想看的不只是"AI 帮我写了多少"，而是"我在哪一步没有听 AI 的"。**
> 这五次否决全部留在对话记录里，可以逐条翻。

## 五、验证

测试集：**30 条真实通知**，全部来自北邮信息服务门户「校内通知」（2026-11-06 至 11-13 发布，
连续三页），覆盖竞赛、讲座、线上课程、志愿招募、体育活动、资助申请、案例征集、教师赛事、
科研申报、后勤事务十类；其中 **12 条是"看起来像机会、实际跟你无关"的负样本**，
2 条是"内容值得但窗口已关"的过期样本。

| 指标 | 结果 |
|---|---|
| 截止日期抽取 | **30 / 30**（100%） |
| 结论方向（值得 / 不值得 / 已过期） | **30 / 30**（100%） |
| 自审误报 | 0（无矛盾的 24 条均未被拦截） |

**评测口径**（不玩文字游戏）：
- 截止日期：以人工逐条标注为准。原文没有报名截止的，解析器**必须**报空——
  给一个错的倒计时比说"没有"更糟。多个截止节点取最早的未过期节点。
- 结论方向：值得 ↔ 强烈建议/可以考虑；不值得 ↔ 不建议/信息不足/待核实；
  已过期 ↔ 已截止。三档分开算，不拿"已截止"冒充"不值得"。
- 这套测试集用 `tools/accuracy.py` 一键复跑，标注写在 `testset/labels.md`。

**首轮实测只有 20% 和 90%**，逐条查出的真问题（这部分才是工程）：

| # | 问题 | 修法 |
|---|---|---|
| 1 | 把门户的「发布时间」当成截止日 | 抽取时剔除元信息行 |
| 2 | 把「活动举办日」当报名截止（讲座类全中） | 截止与举办日彻底分开，没有截止就报空，倒计时改说"天后举办" |
| 3 | 青年教师赛、面向学院报送的征集被打到 83 分 | 先判资格后判分数：抬头面向单位、面向教师/研究生的直接判"不建议" |
| 4 | 后勤停水、电费充值、售房信息被当机会 | 新增「事务」类别，直接排除 |
| 5 | "报名时间"被当成活动时间，误触日期矛盾 | 时间抽取排除报名/截止/申请类字段 |
| 6 | "于 11 月 13 日下班前将……报送"这类写法漏抽 | 增加"于…前"模式兜底，不只靠关键词 |
| 7 | 表格型通知（赛程表、办理窗口）标签与日期分两行，抽不到 | 短标签行（≤20 字且含报名/办理/时间等词）允许跨行取日期 |
| 8 | "比赛时间"被当成报名截止（羽毛球赛报名已过，却显示还能报） | 已有报名/提交节点时，剔除赛程类节点 |
| 9 | 资助类通知被"抬头各学院"误杀 | 正文明确写了面向本科生/研究生的，不按"面向单位"处理 |
| 10 | 招新被识别成竞赛、通行证被识别成其他 | 标题优先判类别 + 类别词表扩充 |

> 第 7–10 条只有第三批通知才暴露。**测试集每加 10 条，就再暴露一批新错**——
> 这就是为什么"30 条真实通知"比"功能列表"更能说明问题。

### 真实用户验证（3 人盲测，2026-11-16）

3 位同学各用**自己微信群里的通知**试用，全程我只发链接、不解释、不指屏幕，截图存档于 `user-feedback/`。

| # | 反馈原话 |
|---|---|
| U1 | 使用起来简明易懂，容易上手 |
| U2 | 倒计时很直观，判据令人信服 |
| U3 | 分数的呈现形式很直观，使用起来也很方便 |

三人不约而同提到**"直观 / 易懂 / 方便"**，没有人卡在操作流程上——呈现层是通的。

**局限（主动写清）**：三人都没有指出判断错误，也没有对结论提出质疑。这说明"好不好看"被验证了，"准不准"没有。样本只有 3 人、全是熟人、用的都是常见类型通知。下一步要用陌生人 + 构造的怪通知去压，才算真正验证。


## 六、边界与已知不足（主动写清）

- 只处理文本，不自动抓取网页（校内门户需登录，爬取不稳定，故不做）。
- 日期缺年份时按当年补全；"次年 3 月"这类跨年通知需人工确认。
- 知识库目前只覆盖推免加分框架、本校赛事情报、志愿服务认定三类；**其他类别会明确显示"未收录依据"，不给假引用**。
- 匹配度是规则加权，不是个性化模型；换一个用户画像，结论会变。
- 本届赛事为第一届校赛，是否进入学院加分认定清单**尚未核实**，作品与说明中均不承诺保研加分。

## 七、一句话总结

它不解决"信息聚合"，它解决**信息差**——因为做它的人，就是被信息差坑过的那个。
