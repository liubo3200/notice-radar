# 通知雷达 NoticeRadar

> 校园通知的机会决策 Agent —— 粘一条通知，告诉你**什么时候截止、值不值得参加、下一步做什么、依据是哪条规定**。

大部分校园信息工具停在"帮你记"，通知雷达往前走一步：**帮你决定**。
它不返回一堆字段，而是返回一个判断——匹配度、理由、风险、引用条款、以及具体到"今天做什么"的行动清单。

---

## 为什么做这个

信息不是没有，是散在群里、门户里、公众号里，而且窗口极短。
一条通知从发布到截止常常只有两三周，漏一次就是漏一届。

这个产品的第一个用户是作者本人：因为没看到通知，错过过一届数学竞赛、一次短视频大赛。
所以它解决的不是"信息聚合"，是**信息差**。

## 五个 Agent 的分工

```
用户粘贴通知
      │
      ▼
┌─────────────┐   抽字段：标题/截止/多截止节点/时间/对象/主办/类别
│  Extractor  │   LLM 优先，失败自动降级规则解析
└──────┬──────┘
       ▼
┌─────────────┐   校验：日期合法性、是否过期、字段完整性、置信度
│  Validator  │
└──────┬──────┘
       ▼
┌─────────────┐   检索：知识库召回真实条款（BM25，带来源标注）
│  Retriever  │   召回不到就返回空，不硬凑引用
└──────┬──────┘
       ▼
┌─────────────┐   评估：匹配度打分 + 引用条款 + 行动清单
│  Evaluator  │
└──────┬──────┘
       ▼
┌─────────────┐   自审：字段矛盾就打回重跑，修不好就明说仅供草稿
│   Critic    │
└──────┬──────┘
       ▼
  决策卡片 + 可导入手机日历的 .ics
```

- **抽取**负责广度，**校验**负责准确，**检索**负责有出处，**评估**负责决策，**自审**负责对账。
- **降级链路**是刻意设计：大模型不可用时规则引擎顶上，页面永远有输出，演示不会翻车。
- **Critic** 抓三类硬矛盾：日期已过却判可报名 / 活动时间早于截止 / 无标题却给强结论。

## 快速开始

```bash
pip install -r requirements.txt
python app.py
```

打开 http://127.0.0.1:8000 ，点上方「竞赛通知」示例，再点「开始解析」。

**不需要配置任何 API Key**，开箱即用（走规则解析 + 知识库检索）。
想用大模型增强，把 `.env.example` 复制为 `.env` 并填三个变量：

```
LLM_BASE_URL=https://你的接口地址/v1
LLM_API_KEY=sk-xxx
LLM_MODEL=模型名
```

Windows 用户可直接双击 `run.bat`。部署见 `docs/部署说明.md`。

## 功能

| 能力 | 说明 |
|---|---|
| 结构化抽取 | 标题、主截止日、**全部截止节点**、活动时间、面向对象、主办单位、类别、链接 |
| 机会评估 | 0–100 匹配度 + 强烈建议/可以考虑/不建议 + 理由与风险 |
| **引用条款** | 从 `knowledge/` 召回规定原文，标注《文件名》§章节；召回不到显示"知识库未收录" |
| **自审机制** | Critic 审查矛盾，打回重跑一次，两轮不通过则标注仅供参考 |
| 行动清单 | 按截止紧迫度给出具体动作，不是泛泛建议 |
| 日历导出 | 生成 .ics，导入手机日历，自带提前 3 天 / 1 天双重提醒 |
| 自动降级 | 无 Key、超时、额度耗尽都不影响出结果 |
| 置信度提示 | 规则解析会明确标注"建议人工复核"，不假装准确 |

## 目录结构

```
notice-radar/
├─ app.py                # Flask 路由 + 五 Agent 编排
├─ core/
│  ├─ parser.py          # ① 抽取（LLM + 规则双通道，多截止节点）
│  ├─ validator.py       # ② 校验
│  ├─ retriever.py       # ③ 知识库检索（中文二元组 BM25，纯标准库）
│  ├─ evaluator.py       # ④ 评估（引用条款）
│  ├─ critic.py          # ⑤ 自审（三类硬矛盾 + 三类软提示）
│  └─ ics.py             # 日历生成（RFC5545）
├─ knowledge/            # 知识库切片（按 ## 小节，带来源）
├─ tools/ingest.py       # 把规定原文切成切片
├─ templates/index.html
├─ static/style.css      # 深色科技风
├─ static/app.js
├─ docs/                 # 部署说明 / 码道 Prompt 序列 / 视频脚本 / 作品说明
├─ Dockerfile · render.yaml
└─ requirements.txt
```

## API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 主页面（`?demo=竞赛` 自动演示） |
| GET | `/api/samples` | 示例通知（含一条故意写错日期的「矛盾通知」） |
| POST | `/api/parse` | `{text}` → 字段 + 校验 + 检索 + 评估 + 自审 |
| POST | `/api/ics` | `{fields, evaluation}` → .ics 文件 |
| GET | `/api/health` | 健康检查 + 知识库切片数量 |

## 知识库怎么加料

把规定原文存成 txt，然后：

```bash
python tools/ingest.py "推免规定.txt" --title "北京邮电大学推荐优秀应届本科毕业生免试攻读研究生管理规定"
```

切好的切片写进 `knowledge/`，服务无需重启（检索器检测文件改动自动重建索引）。

## 实测准确率

30 条真实通知（北邮信息服务门户「校内通知」，连续三页）：

```
截止日期严格命中： 30/30   (100%)
结论方向命中：     30/30   (100%)
```

复跑：`python tools/accuracy.py`。标注在 `testset/labels.md`，原始文本在 `testset/clean/`。

**以上数字可复现，前提是固定时间基准。** 测试集采集于 **2026-11-16**，而"是否过期""最早未过期节点"都依赖当天日期——直接拿现在的真实日期跑，跨过 12 月就会有一两条从"有效"变成"过期"，命中率随之漂移。所以：

- `core/clock.py` 统一了全项目的时间来源（parser / validator / evaluator / critic / ics 都从这里取），不再各自调 `date.today()`；
- `tools/accuracy.py` 启动时把基准日钉死为 `2026-11-16`（测试集采集日），任何时间跑都是 30/30；
- 想换基准日，设环境变量即可：

```bash
NOTICE_RADAR_TODAY=2026-11-16 python tools/accuracy.py
```

线上服务同样支持这个变量：设成某一天，示例通知里的日期都会以该日为原点滚动，"矛盾通知"样例的长跑演示也不会演着演着变成"过期通知"。

## 已知边界

- 只处理**文本**，不自动抓取网页（校内门户需登录，爬取不稳定，故不做）。
- 日期缺年份时按当年补全；跨年通知（如"次年 3 月"）需人工确认。
- 知识库未覆盖的类别会明确显示"未收录依据"，不给假引用。
- 匹配度基于规则权重，当前画像为本科生 / 保研导向。
